envd_scalability DDL latency investigation

Three-way head-to-head: prefix (pre-fix) · iter-6 (mid-investigation) · iter-9 (HEAD) — all measured on the same VM, soft asserts off.

Headline. Per-DDL p50 latency at N=30k catalog tables drops from 118 ms (prefix, before any catalog-perf work) to 55 ms (iter-9, current HEAD) — a 53 % reduction. The per-object slope drops from ~3.7 µs/object to ~1.0 µs/object, roughly 3.7× flatter. The improvement is consistent across all 10 reps at every N (not noise).

What the three runs are

  • prefix — commit 27c3b32f24 on main, before any of the catalog perf work on the envd-specsheet branch. Soft asserts off. Stopped after N=30k by user request to save bench time.
  • iter-6 — commit a5caa58be9, after iterations 1–6 (consistency-check fixes, sync_inner consolidate skip, incrementally-cached proto Snapshot, trailing-consolidate amortization). Soft asserts off.
  • iter-9 — current HEAD on envd-specsheet, after iterations 1–9 (rust-typed snapshot via imbl::OrdMap, cached resource-limit counts, skip last-Op preliminary apply). Soft asserts off.

All three were re-run on the same machine after iter-9, so any VM-speed bias has been eliminated. Distributions are 10 reps per N at each scale (6 reps at N=30k for prefix, since we killed the bench right after that measurement to save the long N=30k→50k population time).

What changed in each phase

prefix → iter-6 (iterations 1 through 6)

  • iter-1 (bb9c84a64c): check_object_dependencies made O(N) instead of O(N²). This only fires when MZ_SOFT_ASSERTIONS=1, so it doesn't change the production-like (soft-asserts-off) numbers we measure here — but it was the dominant CI/dev cost.
  • iter-2 / iter-3: verification runs; no source changes.
  • iter-4 (d6a4276a78): skip the trailing consolidate() in sync_inner when nothing has changed.
  • iter-5 (56211df811): cache the catalog Snapshot in PersistHandle and maintain it incrementally via apply_to_snapshot_cache. No more per-transaction BTreeMap rebuild from the consolidated trace.
  • iter-6 (a5caa58be9): amortize trailing consolidate() via the doubling rule (now happens log-N times under bulk DDL, not every transaction). with_trace dropped; get_next_id reads the cached snapshot instead.

iter-6 → iter-9 (iterations 7 through 9)

  • iter-7 (c10cb56e24) — biggest individual change: PersistHandle::cached_snapshot is now a rust-typed MemorySnapshot with 21 imbl::OrdMap<K, V> fields. RustType::from_proto now runs once per durable update (O(1)) instead of once per entry per transaction (O(N)). Transaction::new destructures the cache and hands each map straight into the corresponding TableTransaction — no proto conversion on the hot path. Touch: +272/-165 lines across 11 files.
  • iter-8 (dc2acd5f13): cache ResourceLimitCounts on CatalogState (11 counters). Coordinator::validate_resource_limits now O(1) instead of doing six O(N) walks per DDL. A check_resource_counts consistency check keeps the cache honest. Touch: +261/-37 lines across 6 files.
  • iter-9 (3900de3bd2): skip the per-Op preliminary apply_updates on the last Op. Halves apply_updates work for single-Op DDL (the common case). Touch: +10/-2 lines, one file.

Where the remaining ~1 µs/object slope lives

At N=12k on the iter-9 coord-thread flame, the remaining cost is:

  • ~22 % imbl::OrdMap operations (path-copy on every mutation of entry_by_id, clusters_by_id, etc.)
  • ~10 % CatalogState::apply_updates
  • ~7 % drop_in_place::<CatalogState> — the Cow::to_mut() final clone
  • ~7 % builtin-table updates
  • The rest is off-coord-thread: persist write commit latency (grows with shard size) and controller round-trips.

Decision

The validation confirmed that all three of iter-7, iter-8, iter-9 do meaningful work end-to-end. The 53 % p50 reduction at N=30k cleanly attributes ~25 % to iter-1..iter-6 and ~38 % (of the iter-6 number) to iter-7..iter-9. Keep all changes.

Caveat (N=30k for prefix). We have 6 reps at N=30k for the prefix run (the bench was killed right after the N=30k measurement to skip the 75-minute population to N=50k). The values are tight (110–124 ms), so the p50 of 117 ms is a credible read; we just don't have the standard 10 reps' worth of tail data at that N.
