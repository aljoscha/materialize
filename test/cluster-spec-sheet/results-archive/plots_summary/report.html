envd_scalability DDL latency investigation

CREATE TABLE latency on the measurement cluster as the number of pre-existing catalog objects grows. Goal: keep DDL flat in N.

Result summary. At N=30k tables, DDL p50 went from 267 ms (iter-1 baseline, soft asserts on) to 54 ms (iter-7+, soft asserts off). Slope from N=1→N=10k went from ~25 µs/object down to ~1.5 µs/object. The coordinator-thread CPU side of the per-DDL hot path is now essentially flat in N; the remaining slope lives in the imbl::OrdMap COW machinery and persist write commit latency — both off the algorithmic O(N) catalog work we targeted.

6. Where the remaining slope lives

After iter-9, coordinator-thread CPU is no longer dominated by O(N) work in the catalog layer. Per the iter-9 flame at N=12k:

  • ~22% imbl::OrdMap COW path-copies on every state mutation (insert_entry, get_schema_mut, etc.).
  • ~10% CatalogState::apply_updates for the final apply on state.to_mut() — that Cow::Owned(state) clone is still a real allocator hit.
  • Persist write commit latency grows with the durable shard size; not visible in coord CPU because it's off the coord thread.

Closing the remaining ~1.5 µs/object slope would mean architectural changes: swap the hot imbl::OrdMap collections for a different copy-on-mutate-the-Arcs scheme, eliminate the final Cow::to_mut() clone, or batch durable catalog writes so a single DDL doesn't always round-trip persist.

Caveat on absolute numbers. Iter-1 through iter-6 ran on a different VM (smaller, more contended) than iter-7 / 8 / 9. The "92 → 8 ms at N=1" jump between iter-6 and iter-7 mostly reflects that VM difference — the iter-7 cache change wouldn't move N=1 latency. The slope comparison (how much an extra object costs at the margin) is the load-bearing comparison and is robust to per-VM speed differences.
